# Architecture Review
Generated: 2026-09-15T22:38:39.646Z
Score: 72/100

## Summary
The codebase follows a mostly consistent packet-based architecture (repos → services → hooks → pages) with decent separation of concerns and defensive SDK-boundary handling, but it carries a legacy scaffold artifact (lib/contract.ts) that duplicates the real domain types with incompatible shapes, several copy-pasted utility patterns (haptics, KST date formatting, localStorage wrappers) that should be centralized, and inconsistent API-access/error-handling conventions between hooks and services. Test organization is split across three different conventions. None of these are fatal, but they add real maintenance risk as more packets are added.

## Issues
### Critical
- [structure] Two parallel, incompatible domain type systems coexist: src/lib/contract.ts declares generic scaffold types (Flow, Run, Log, Trigger, Action with `config: Record<string, any>`) while src/types/*.ts declare the real discriminated-union types with the same names (Flow, Trigger, Action) but different shapes. Both are actively imported side-by-side (metrics.ts imports `Run as ContractRun`, validateDraft.ts imports `Flow as ContractFlow`), and lib/contract.ts's useAppStateFn/apiClientFn/executeFlowFn signatures no longer match the real useAppState/apiClient/runService implementations. — Files: src/lib/contract.ts, src/types/flow.ts, src/types/run.ts, src/lib/metrics.ts, src/lib/validateDraft.ts / Fix: Retire lib/contract.ts once all packets are implemented (it's documented as scaffold-only), or rename its types (e.g. ContractFlow/ContractRun) consistently everywhere and reconcile signatures with actual implementations so it stops silently drifting from reality.

### Warnings
- [duplication] The 'call generateHapticFeedback, swallow throw outside WebView' pattern is copy-pasted with slightly different implementations (some wrap in Promise.resolve().catch(), some don't) across at least 7 files: BottomCTA.tsx (fireHaptic), Home.tsx (fireHaptic), FloatingTabBar.tsx (inline), Builder.tsx (tick), ActionListSheet.tsx (tick), AiStepSheet.tsx (tick), TriggerInputSheet.tsx (tick), AiNoticeDialog.tsx (inline). — Files: src/components/BottomCTA.tsx, src/pages/Home.tsx, src/components/FloatingTabBar.tsx, src/pages/Builder.tsx, src/components/builder/ActionListSheet.tsx, src/components/builder/AiStepSheet.tsx, src/components/builder/TriggerInputSheet.tsx, src/components/AiNoticeDialog.tsx / Fix: Extract a single `src/lib/haptics.ts` with `fireHaptic(type)` that always wraps in Promise.resolve().catch() and swallows the WebView-outside throw, then import it everywhere instead of redefining local tick()/fireHaptic() helpers.
- [duplication] Three separate localStorage abstraction layers exist with different names doing overlapping work: src/lib/storage.ts (getItem/setItem/removeItem, no corruption handling), src/lib/safeStorage.ts (readSafeStorage/writeSafeStorage, quota + corruption handling), and src/lib/repos/shared.ts (readEntity/writeEntity, corruption backup handling, built on writeSafeStorage). storage.ts appears to be dead/superseded but still exists as a competing API. — Files: src/lib/storage.ts, src/lib/safeStorage.ts, src/lib/repos/shared.ts / Fix: Delete src/lib/storage.ts if unused (confirm with a repo-wide reference search), and keep repos/shared.ts as the single sanctioned entry point for localStorage access, built on safeStorage.ts internals.
- [consistency] API access pattern is inconsistent: services (runService, scheduleService) call typed/validated wrappers from api/endpoints.ts (startRun, updateSchedule, deleteSchedule), but useGenerateSubmit.ts calls `apiClient.post` directly and blindly casts the JSON response to GenerateResponseBody, bypassing the assertValid/GenerateResponse.isValid validation that endpoints.ts otherwise enforces for every other call. — Files: src/hooks/useGenerateSubmit.ts, src/api/endpoints.ts, src/api/client.ts / Fix: Route the /generate call through a typed function in api/endpoints.ts (or add one) so all API responses go through the same isValid guard before being trusted by callers.

### Suggestions
- [duplication] formatKSTDateTime (FlowDetail.tsx) and formatKSTStartedAt (RunDetail.tsx) are near-identical Intl.DateTimeFormat wrappers for Asia/Seoul timestamps, differing only in the month/day/hour formatting options, duplicated instead of being parameterized in lib/time.ts. — Files: src/pages/FlowDetail.tsx, src/pages/RunDetail.tsx, src/lib/time.ts / Fix: Add a shared `formatKSTDateTime(iso, options)` helper to lib/time.ts and have both pages call it with their specific Intl options.
- [consistency] Error handling conventions differ across services: scheduleService/flowRepo throw plain `new Error('메시지')`, runService/api layer throw the structured `ApiError` with a code, and FlowLimitError encodes its type as a string prefix on the message ('FlowLimitError: ...') that callers must regex-strip (see useBuilderSave.ts) rather than reading a typed field. — Files: src/lib/errors.ts, src/hooks/useBuilderSave.ts, src/services/scheduleService.ts, src/lib/repos/flowRepo.ts / Fix: Standardize on typed error classes with a clean `.message` (no prefix stripping) and a discriminant field, consistent with how ApiError already exposes `.code`.
- [structure] Test files are organized under three different conventions simultaneously: co-located `*.test.tsx` next to source (App.test.tsx, builder.test.tsx, RunDetail.test.tsx, validateDraft.test.ts, services.test.ts), a dedicated `src/test/` folder (adPlacement.test.tsx, policy.test.ts, setup.ts), and a `src/__tests__/` folder (helpers, packet-0004.test.ts referenced but not shown). — Files: src/App.test.tsx, src/test/adPlacement.test.tsx, src/test/policy.test.ts, src/components/builder/builder.test.tsx / Fix: Pick one convention (co-located is already dominant) and move src/test/adPlacement.test.tsx and policy.test.ts to be co-located with what they test, or document the three-tier split explicitly (e.g. src/test/ reserved for cross-cutting policy/layout checks) so it reads as intentional rather than inconsistent.
- [dead_code] formatCurrency and cn in src/lib/utils.ts are not referenced by any shown component or page — Amount.tsx/CountUp.tsx use formatNumber only, and no className-composition usage of cn appears anywhere. — Files: src/lib/utils.ts / Fix: Verify with a repo-wide grep; if genuinely unused, remove them or move to a `utils.ts` reserved explicitly for future/shared use with a comment explaining why they're kept.
- [naming] src/lib/format.ts exports a function literally named `format` (draft => one-line summary string), which is an overly generic name that shadows the common verb 'format' used throughout the file for other purposes (formatTrigger, formatAiStep, formatDuration), making call sites like `format(draft)` hard to grep/understand in isolation. — Files: src/lib/format.ts, src/pages/Builder.tsx, src/pages/FlowDetail.tsx, src/pages/GenerateResult.tsx, src/pages/Home.tsx / Fix: Rename the default summary function to something specific like `formatDraftSummary` or `summarizeDraft`.
- [circular_dep] src/lib/types.ts re-exports from '@/api/contracts', while src/api/contracts.ts imports `type { Flow, RunLog, Trigger }` from '@/lib/types' — a type-only circular import. TypeScript's `import type` erasure makes this safe at runtime, but it's structurally circular and fragile if either file adds a value-level export or barrel re-export later. — Files: src/lib/types.ts, src/api/contracts.ts / Fix: Have api/contracts.ts import directly from the concrete source modules (@/types/flow, @/types/run) instead of the aggregating @/lib/types barrel, breaking the cycle at its root.
